Federal Compliance Deadline: April 2027

The DOJ Final Rule (28 CFR Part 35, published April 2024) requires all state and local government entities to make their web content and PDFs accessible to WCAG 2.1 Level AA standards. Entities serving populations of 50,000+ must comply by April 2026. All remaining entities must comply by April 2027. Non-compliant PDFs are legally actionable under Title II of the Americans with Disabilities Act.

The Law

ADA Title II — Digital Accessibility

Title II of the Americans with Disabilities Act (42 U.S.C. § 12132) prohibits state and local government entities from discriminating against people with disabilities in their programs, services, and activities. The DOJ has clarified that this includes all digital content — websites, web applications, and PDFs.

DOJ Final Rule — 28 CFR Part 35 (April 2024) For the first time, the DOJ has issued a specific technical standard. All state and local government digital content must conform to WCAG 2.1 Level AA. This includes PDF documents made available on government websites or portals. The rule was published April 24, 2024.

Who must comply?

Any state or local government entity that provides programs, services, or activities to the public is covered. This includes:

  • State agencies and departments
  • County and municipal governments
  • Courts and judicial agencies
  • Public universities and community colleges
  • Public school districts
  • Public hospitals and health departments
  • Transit authorities and utility districts

Compliance deadlines

Non-compliance risk Failure to comply can result in DOJ enforcement action, administrative complaints, and private lawsuits under Title II. Courts have awarded significant damages in ADA digital-accessibility cases. Remediating documents before the deadline is far less expensive than litigation.
The Law

Section 508 of the Rehabilitation Act

Section 508 (29 U.S.C. § 794d) requires all federal agencies to make their electronic and information technology — including PDFs — accessible to people with disabilities. While technically limited to federal agencies, Section 508 standards have been adopted by many state governments and are the technical framework behind government PDF accessibility requirements.

Section 508 refresh (January 2018) The Revised Section 508 Standards align with WCAG 2.0 Level AA (now interpreted as WCAG 2.1 AA) and with PDF/UA (ISO 14289-1). All PDFs published by federal agencies must comply. The HHS Section 508 Program Office publishes official guidance on PDF tagging.

Key Section 508 requirements for PDFs

  • All PDF content must be tagged using the PDF tagging structure defined in PDF/UA
  • Document language must be set (e.g., en-US)
  • Document title must appear in document properties
  • Reading order must match visual presentation order
  • All meaningful images must have alternative text
  • Tables must identify header cells with scope attributes
  • Color alone cannot be used to convey information
  • Minimum contrast ratio 4.5:1 for normal text, 3:1 for large text
Standard

WCAG 2.1 Level AA

The Web Content Accessibility Guidelines (WCAG) 2.1, published by the W3C, define the technical standard for accessible digital content. The DOJ Final Rule mandates WCAG 2.1 Level AA compliance. WCAG is organized around four core principles:

P

Perceivable

Information must be presentable in ways users can perceive. Alt text for images, captions for video, sufficient color contrast, and content that does not rely solely on sensory characteristics.

O

Operable

Functionality must be operable through a keyboard alone. No timing traps, no flashing content that could cause seizures, and navigation landmarks so users can find content.

U

Understandable

Content must be readable and understandable. Document language set, labels on form fields, error identification and suggestions, consistent navigation.

R

Robust

Content must be robust enough for assistive technologies to interpret reliably. PDF tags must follow the PDF/UA specification so screen readers can parse them correctly.

Standard

PDF/UA — ISO 14289-1

PDF/UA (Universal Accessibility) is the ISO standard that defines exactly how PDF tagging must be structured so that assistive technologies (screen readers, braille displays) can correctly interpret documents. Conforming to PDF/UA is the clearest way to demonstrate Section 508 / WCAG 2.1 compliance for PDFs.

PDF/UA core requirements
  • Document must have a tagged PDF flag (/MarkInfo <</Marked true>>)
  • Document must have a structure tree (/StructTreeRoot)
  • All real content must be tagged; decorative content must be marked as artifacts
  • Every tag must use a standard PDF tag type or map to one via role map
  • Tables must have TH tags with Scope attribute
  • Figures must have /Alt attribute (alt text)
  • Headings must be nested logically (H1 → H2 → H3, no skipping levels)
  • Document language must be declared (/Lang)
  • Document title must appear in XMP metadata
PDF Tagging

What is PDF tagging?

A PDF can look perfect on screen while being completely inaccessible to screen readers. The difference is PDF tags — a hidden layer of semantic markup embedded in the PDF file that tells assistive technologies what each element is: a heading, a paragraph, a table cell, an image with alt text.

An untagged PDF renders as a flat image to a screen reader. A properly tagged PDF allows a blind user to navigate headings, read tables, hear image descriptions, and understand the document's logical structure.

Source: HHS Section 508 Tagging Guide (May 2018) The following tag rules are derived from the official HHS Section 508 Program Office guide — Tagging PDFs in Adobe Acrobat Pro. This is the governing reference for how federal agencies tag PDFs to meet Section 508 requirements.

The tag tree structure

Every accessible PDF has a tag tree — a hierarchy of tags that parallels the document's visual layout. The tree starts at a Document root and contains nested structural elements. The order of tags in the tree defines the reading order for assistive technologies, regardless of visual position on the page.

PDF Tagging

Headings (H1 – H6)

Headings allow screen reader users to navigate documents efficiently by jumping between sections. Proper heading structure is one of the most important accessibility requirements.

Rules for heading tags
  • Use H1 for the document's main title (once per document)
  • Use H2 for major section titles
  • Use H3–H6 for subsection headings, always nested inside the parent level
  • Never skip levels — going from H2 to H4 without H3 is non-compliant
  • Only use heading tags for structural headings, not for bold or large text that is decorative
  • Running headers that repeat on every page (e.g., agency name, document title at top of each page) are artifacts, not H tags

Common mistakes

  • Marking every bold text as a heading regardless of its role in the document structure
  • Using H1 multiple times for different section titles on the same page
  • Marking page header/footer repeating text as headings (these should be artifacts)
  • Skipping from H1 directly to H3 for first subsection
PDF Tagging

Paragraphs (P)

Body text must be tagged with the P (paragraph) tag. Each distinct block of body text should be its own P element. Multi-column layouts should have reading order that flows logically column by column, not left-to-right across all columns on a single line.

Rules for paragraph tags
  • Each paragraph is a single P tag — do not split one paragraph across multiple tags
  • The text order in the tag tree must match the intended reading order
  • In multi-column layouts, the left column's text must come before right column text in the tag tree
  • Inline formatting (bold, italic) can be wrapped in Span elements inside a P
PDF Tagging

Tables (Table / TR / TH / TD)

Tables are one of the most complex elements to tag correctly. A screen reader user navigating a table needs to hear which header applies to each data cell. This requires proper TH tags with Scope attributes.

Rules for table tags
  • Table — wraps the entire table
  • TR — each row of the table
  • TH — header cells. Must include a Scope attribute: Scope="Column" for column headers, Scope="Row" for row headers, Scope="Both" for cells that are both
  • TD — data cells
  • A table that looks like a layout table (not data) should either be tagged as a data table with appropriate headers, or tagged as an artifact if it contains no meaningful content
  • Merged cells must use ColSpan and RowSpan attributes

Example tag structure for a simple table

Table
  TR
    TH (Scope="Column") → "Name"
    TH (Scope="Column") → "Department"
    TH (Scope="Column") → "Phone"
  TR
    TD → "John Smith"
    TD → "Finance"
    TD → "555-1234"
PDF Tagging

Images and Figures (Figure)

Every meaningful image must be tagged as a Figure and include alternative text. Alternative text is read aloud by screen readers in place of the image.

Rules for Figure tags and alt text
  • Tag meaningful images with Figure
  • Set the /Alt attribute on the Figure tag to provide alternative text
  • Alt text should be 120–250 characters: long enough to be descriptive, short enough to be scannable
  • Describe what the image communicates, not what it looks like literally — e.g., "Bar chart showing 34% increase in applications from 2022 to 2023" not "image of a bar chart"
  • Do not begin alt text with "image of" or "picture of" — screen readers already announce "graphic"
  • Decorative images (dividers, backgrounds, logos used for branding only) must be tagged as Artifact, not Figure, so screen readers skip them
  • Images of text (scanned text) must include all the text content in the alt text, or the document must also provide the text in the body

PDF Tagging

Lists (L / LI / Lbl / LBody)

Bullet points and numbered lists must use the full list tag structure. Simply having a bullet character in a paragraph tag is not sufficient — screen readers need the structural tags to announce "list of 5 items, item 1 of 5."

Rules for list tags
  • L — the list container (wraps all list items)
  • LI — each list item
  • Lbl — the bullet, number, or label (inside LI)
  • LBody — the text content of the list item (inside LI)
  • Nested lists: an L tag can be placed inside an LI → LBody to create a sub-list
  • The label character (bullet "•" or number "1.") must be in the Lbl tag, not embedded in the LBody text

Example tag structure

L
  LI
    Lbl → "•"
    LBody → "First item text"
  LI
    Lbl → "•"
    LBody → "Second item text"
PDF Tagging

Links (Link)

Hyperlinks must be tagged so screen readers can identify and activate them. Bare URLs in text are not sufficient — the link must have a meaningful label and be tagged properly.

Rules for link tags
  • Tag each hyperlink with the Link tag
  • The link must have a meaningful label — e.g., "Download the 2023 Annual Report" not "click here" or the bare URL
  • Include an OBJR (object reference) inside the Link tag that references the PDF annotation
  • Link text must be unique on the page — two links that say "Download" but go to different URLs are non-compliant
  • Links that open a new window must warn the user: "Download the Annual Report (opens in new tab)"
PDF Tagging

Artifacts (decorative / non-content elements)

Not every element in a PDF needs to be read by a screen reader. Decorative elements, repeated page headers/footers, page numbers, and background graphics should be marked as Artifacts so screen readers skip them entirely.

What should be an artifact?
  • Page numbers
  • Running headers/footers that repeat on every page (agency name, document title at page top)
  • Decorative lines, borders, and background graphics
  • Watermarks
  • Logos used only for branding (not conveying information)
  • Section dividers
Artifacts vs. content — a common mistake The running header "U.S. Department of Labor — Wage and Hour Division" repeating at the top of each page is an artifact. The document's actual title on the first page is an H1. Confusing these is one of the most common tagging errors — if a running header is tagged as H1, screen reader users will hear the agency name announced as the heading every time they navigate the document.
Testing

Testing accessibility in Adobe Acrobat Pro

Adobe Acrobat Pro includes a built-in Accessibility Checker that is the primary tool used by government compliance officers to verify PDF accessibility. Running this check before publishing any PDF is essential.

How to run the Acrobat Pro Accessibility Checker

  1. Open the PDF in Adobe Acrobat Pro (not Reader)
  2. Go to Tools → Accessibility → Accessibility Check
  3. In the dialog, check all categories and click Start Checking
  4. Review the Accessibility Checker Results panel — fix all Errors and Warnings
  5. Right-click on any failed item to see the issue details and Acrobat's suggested fix
  6. Re-run the checker after fixes until all items show a checkmark
